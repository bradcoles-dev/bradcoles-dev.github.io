From Imperative to Declarative: How Data Engineering Found a Better Way

Notebook-first workloads are being replaced. Not overnight, and not entirely — but the direction of travel is clear. This covers what the shift looks like in practice, how it played out historically, and how to think about moving forward.

Brad Coles · May 2026

Declarative programming has been gaining momentum across the data engineering stack over the past decade. The transformation layer got there first — heralded in by dbt back in 2016, with data engineering teams slowly but surely replacing their notebook-first workloads and not looking back. But the shift hasn't stopped at transformation. Ingestion tools like Fivetran, Airbyte, Fabric's Copy Job, and Databricks' Lakeflow Connect have brought the same idea to the Extract and Load steps — you declare what you want moved and where, and the platform handles execution, schema changes, and incremental state. The whole ELT stack is moving in the same direction.

But what exactly does declarative mean, and how does it differ from the way most teams work today? You've probably heard of dbt and SQLMesh. If you're on Databricks, Snowflake, or Fabric you're likely aware of Delta Live Tables, Dynamic Tables, or Materialized Lake Views. It's not the vendor or the tool that matters — it's the underlying approach.

Think of it like a house renovation. Notebook transformations are like telling your tradespeople which wall goes where, at what size and in which order. Declarative transformations are more like handing the builder a set of plans and letting them own the process.

This article covers what that shift looks like in practice, how it played out historically, why it's gained traction, and how to think about moving forward.

1. What: Imperative vs. Declarative

The terms get thrown around a lot, so it's worth being clear about what they actually mean.

Procedural programming (a sub-class of imperative) is what most data engineers have been doing for years — you write explicit, step-by-step instructions. Read this table, filter these rows, join here, write the output there. You define the order, manage the control flow, and handle each step yourself.

Declarative programming flips this around — you describe what the output should look like, and the system works out how to produce it.

One quick clarification, because it tends to come up: SQL has always been declarative. When you write SELECT * FROM orders WHERE status = 'pending', you're describing what you want — not which index to use or how to scan the table. Early ETL tools like DataStage and Informatica had visual drag-and-drop interfaces that were also declarative in spirit.

The shift we're talking about isn't about SQL the language, or graphical ETL designers. It's about the framework built around SQL — how dependencies between models get managed, how testing gets enforced, how documentation stays current, and whether your business logic is tied to a specific execution engine or not. That's what's changed.

A concrete example: SCD Type 2. In an imperative approach, you write the logic yourself — join new data to the existing table on the business key, check whether any tracked columns have changed, end-date the old row, insert a new version. In PySpark that's roughly 30 lines of Delta merge logic, and you own every edge case.

In a declarative framework, you describe what you want:

snapshots:
  - name: customers
    config:
      unique_key: customer_id
      strategy: timestamp
      updated_at: updated_at

Run dbt snapshot. The framework handles the comparison, the end-dating, and the insert. You declared the desired outcome — track history on this table using this key — and the system worked out the how.

3. Why: The Cost of Procedural at Scale

The problem with notebooks

PySpark notebooks are genuinely good at certain things — ML feature engineering, complex Python logic, and bespoke ingestion work that dedicated EL tools don't handle. Plenty of teams use Fivetran, Azure Data Factory, or Airbyte for ingestion and never open a notebook for it.

And to be fair, notebooks have worked perfectly fine for transformation too. Teams have been doing it for years and shipping production pipelines with them. The question isn't really whether notebooks work — they do — it's whether declarative frameworks do it better.

For the transformation layer specifically, here's how they compare:

Procedural notebooks Declarative frameworks
Dependencies Execution order implied by cell position. Downstream impact when you change an upstream model is yours to track manually. You declare relationships between models; the framework determines execution order automatically.
Error detection Fails at runtime — a broken column reference, a schema change, a typo in a join key only surfaces when the job actually executes. Errors surface at compile time, before a single row is processed.
Testing Whatever someone remembered to write. No standard framework, no consistent enforcement. Data quality constraints declared alongside the model definition. Run automatically.
Documentation Wikis and comments go stale as code evolves. No mechanism to keep them in sync. Generated from the same source as the logic. Always in sync.
Version control Notebooks stored as JSON. Diffs are noisy and hard to review — cell metadata and output state mix with logic. Merge conflicts in multi-developer teams are painful. Plain SQL files. Clean diffs. Meaningful code review.
Portability Business logic coupled to the execution engine — PySpark DataFrames don't travel. Portable SQL. Swap the adapter or platform; the logic stays intact.

At small scale, the notebook approach is perfectly manageable. As the codebase grows and more people touch it, the gaps in the left column start to compound — and that's where declarative frameworks tend to pull ahead.

Why every major platform arrived at the same answer

If you want evidence that the shift is real, look at what the major platforms have done independently:

  • Snowflake built Dynamic Tables. Databricks built Delta Live Tables (now Lakeflow). Microsoft built Materialized Lake Views.
  • In February 2022, Snowflake and Databricks both invested in dbt Labs — then shipped their own competing native tools within months.
  • In October 2025, Fivetran — the leading EL platform — merged with dbt Labs at ~$600M ARR. The company owning the Extract and Load merged with the company owning the Transform.
  • In June 2025, Databricks contributed Spark Declarative Pipelines (SDP) to Apache Spark — not a straight open-sourcing of DLT, but a new framework built on lessons learned from running DLT in production at scale. It shipped as a headline feature in Spark 4.1.0 in December 2025. Databricks didn't just build a declarative tool; they used it to inform an open standard for the broader ecosystem.

Snowflake and Microsoft got there independently. Databricks got there first and then open-sourced their answer. Either way, the direction is the same.

4. How: Moving Forward

Scope first

The declarative shift is happening across the whole ELT stack — but the tooling is most mature, and the evidence most compelling, in the transformation layer. That's where most of this article has focused.

Common ingestion patterns are increasingly declarative too. Fivetran, Airbyte, and Microsoft Fabric's Copy Job all follow the same principle — you declare which sources and destinations to connect, what to copy and how, and the platform handles execution, schema changes, and incremental state. Lakeflow Connect on Databricks takes the same approach. You configure the desired outcome; the tool owns the how.

Where procedural code still makes sense: complex API ingestion with custom authentication, bespoke data sources, streaming, ML inference, complex nested data, and iterative algorithms. These legitimately need Python and PySpark, and declarative tools don't try to replace them.

The transformation layer is where the shift has been most pronounced and where the tooling is most mature — stable, well-defined, SQL-expressible business logic that turns landed data into clean, trusted models. That's where the notebook costs compound most visibly, and that's where declarative tools have the clearest payoff. But the direction of travel for the broader stack is the same.

The declarative spectrum

Not all declarative tools are declarative in the same way, and understanding the differences helps you pick the right starting point.

Interface-level declarative — dbt and similar frameworks

dbt Labs describes it well: "dbt takes a declarative approach to managing datasets by using SELECT statements to describe the set of data that should make up the table." You describe the desired end state, and the framework handles dependency resolution, materialisation, and testing. Worth being transparent though — at the execution level, dbt is running an imperative sequence of SQL mutations against a mutable database. It's declarative in what you write, not necessarily in how it executes. Think of it like Makefiles — declarative-looking rules, imperative underneath. For most teams moving away from notebooks, this is the right and sufficient starting point.

Execution-level declarative — SQLMesh

SQLMesh explicitly markets itself as declarative and is built to back that claim at the execution level too. MODEL blocks declare properties, dependencies, update methods, and schedules directly in code. Its plan/apply workflow shows you exactly what will change before anything executes. Virtual environments let you test pipeline changes in isolation without touching production. If you want declarativeness at the execution level — not just the interface — SQLMesh is the more rigorous choice.

Platform-native declarative — Dynamic Tables, Lakeflow, MLVs, Spark SDP

If you're already committed to a single platform, the native tooling is worth a look. No framework to install, no adapter to configure. The trade-off is portability — these tools are tied to their host platform in ways that open-source frameworks aren't.

A general caveat — leaky abstractions

Declarative tools abstract away execution, which is mostly the point. But abstractions are leaky, and when they break down you feel it. You lose some of the granular control that imperative code gives you — specific compute configurations, spot instance selection, fine-grained performance tuning. For most transformation workloads this doesn't matter. For teams with complex performance or cost requirements, it's worth knowing upfront that you're trading control for convenience, and occasionally you'll hit the edges of what the abstraction covers.

Where to start

If you're on… Worth considering…
SSIS / legacy ETL tools A SQL-first declarative framework — dbt Core is the most widely adopted starting point. The jump is significant but the payoff is proportional.
PySpark notebooks on Databricks Databricks Lakeflow (platform-native, minimal setup) or an open-source framework if portability matters
PySpark notebooks on Microsoft Fabric Fabric's native Materialized Lake Views for low friction, or an open-source framework for richer testing and portability
Already on dbt, want more rigour SQLMesh — plan/apply, virtual environments, execution-level state management

You don't need to migrate everything at once. The typical pattern is to start with one domain — a staging layer, a single subject area — run it alongside existing notebooks, and compare. The difference tends to be obvious pretty quickly.

Notebooks don't disappear — they just get used where they're actually needed: ingestion, streaming, ML, complex Python logic. Going back to the house analogy: handing the builder a set of plans doesn't mean tools stop being used on site. It just means they're used where they're needed, not for everything by default.
