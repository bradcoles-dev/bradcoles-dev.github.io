Microsoft Fabric Mirroring: Everything You Need Before You Commit

A practitioner's depth guide — connectors, limits, cost, architecture trade-offs, and the edge cases that only surface in production.

By Brad Coles | Senior Consultant & Data Engineering Capability Lead, Synechron Australia

Accuracy notice: This post was written in May 2026 and reflects the state of Microsoft Fabric mirroring at that time. Fabric is a rapidly evolving platform — features that are in Preview today may reach GA with changed behaviour, documented limitations may be resolved, and new connectors or capabilities may be added. Before making architectural decisions based on this post, verify current behaviour against the official Microsoft documentation. Where this post identifies something as a gap or limitation, check whether it has been addressed in a recent Fabric release.

Microsoft Fabric mirroring promises a lot: near-real-time analytics on your operational data, zero ETL pipelines, no compute charges for ingestion, and a seamless path from source database to Power BI report. For a large class of use cases, it genuinely delivers. Most practitioners encounter the limits not through the documentation (which is structured for breadth) but through production, which is a more expensive place to discover them.

This article is built on close study of mirroring across successive releases: the documentation as it shipped, community-reported production behaviour, and the connector limitations scattered across ten separate pages. Data type limitations that previously blocked whole categories of source tables have been addressed or narrowed as the feature has evolved. Meaningful limitations remain — what mirroring replicates, what it silently drops, and what it cannot preserve — and this article works through them.

This post is for data engineers, architects, and analysts evaluating mirroring for production use. It is not a getting-started tutorial — the official documentation covers that ground well enough. It is a depth guide for practitioners who have moved past the overview: connector-specific behaviour, architectural trade-offs, operational limits, and the edge cases that only surface in production. The appendix consolidates capability support across all ten connectors into a single reference matrix — including the gaps where Microsoft has not published documentation — so you can assess your specific source without cross-referencing ten separate limitations pages.

The three types of mirroring

The word "mirroring" covers three architecturally distinct mechanisms. Choosing the wrong one for your use case is the first and most common mistake.

Type Data movement Requires Best for
Database mirroring Replicated to OneLake as Delta/Parquet Native connector for your source Low-latency analytics without querying the source directly
Metadata mirroring Stays in source; OneLake shortcuts created Azure Databricks or Dremio Unified Fabric experience over data already in a supported catalog
Open mirroring You write files; Fabric merges them into Delta Any system that can write Parquet or delimited text to OneLake No native connector exists, or you need full control over change tracking

1. Database mirroring — data moves

The source database's change log (CDC, Change Tracking, or Fabric's own Change Event Stream) is continuously read, and changes are replicated as Delta/Parquet files into OneLake. The data lives in Fabric. Queries hit OneLake, not the source.

Use this when you want low-latency analytics without hitting the production database, and your source is one of the supported connectors: Azure SQL Database, Azure SQL Managed Instance, SQL Server, PostgreSQL, MySQL, Oracle, Snowflake, Cosmos DB, Google BigQuery, or SAP. One important exception: SAP is not a direct connection. It routes through SAP Datasphere as an intermediary, which must be separately licensed and configured.

One special case worth noting: Fabric SQL database (Microsoft's own managed SQL database within Fabric) is mirrored to OneLake automatically, with no setup, no connector configuration, and no source-side changes required. If your operational workload is running on Fabric SQL database, the analytics layer comes for free.

2. Metadata mirroring — data stays put

The source data is not copied. Instead, OneLake shortcuts are created that point to the source. Querying the "mirrored" item queries the source system in real time — query performance depends on the source system's responsiveness, not OneLake.

Use this when you want the Fabric SQL analytics experience over data that already lives in a supported catalog: Azure Databricks or Dremio. A caveat applies to both: neither vendor documents the integration from their own side — it is covered only in Microsoft's documentation. Dremio has an additional flag: Microsoft's own page marks it as Preview while the mirroring overview table does not. Treat both connectors as early-stage and test thoroughly before committing.

3. Open mirroring — you write the data

You deliver files (Parquet or delimited text) to a OneLake landing zone in a prescribed format. Fabric's replication engine picks them up and merges them into Delta tables. No Microsoft connector required; any system that can write files can feed the pipeline.

Use this when no native connector exists for your source, or when you need full control over what gets replicated and how changes are tracked. It has the steepest setup curve of the three types but the widest applicability. The partners ecosystem lists pre-built integrations for common systems.

Each connector is its own evaluation

The three-type taxonomy above is a useful starting point, but it understates the variation within database mirroring. Each connector uses a different change capture mechanism:

  • SQL Change Feed for Azure SQL Database
  • CDC for SQL Server 2016–2022
  • Change Event Stream for SQL Server 2025
  • logical replication for PostgreSQL
  • binary logs for MySQL
  • LogMiner for Oracle
  • Snowflake Streams for Snowflake
  • built-in change feed for Cosmos DB

Each has different data type support, different DDL handling, different source-side prerequisites, and different maturity. Each change capture mechanism has its own operational profile and documented constraints.

The practitioner must treat each connector as its own evaluation. Nothing generalises cleanly across connectors unless the documentation explicitly says it does. A limitation on Azure SQL Database may not apply to PostgreSQL, and a behaviour confirmed for Cosmos DB tells you nothing about BigQuery.

It is a proxy for documentation maturity rather than feature completeness: Azure SQL Database and SQL Server score 4 each due to undocumented DDL edge cases rather than fundamental unknowns, while BigQuery's 9 gaps include basic operational questions like whether ADD COLUMN is handled at all.

What works well

Where mirroring operates within its intended scope, it delivers.

The cost model is real

The replication compute does not consume Fabric capacity — documented and confirmed by independent benchmarking. Storage is free up to 1 TB per capacity unit. The compelling advantage is not raw CU savings over a carefully built pipeline — it is continuous near-real-time replication at near-zero ingestion cost, a cadence that would be unworkable via scheduled pipelines on any reasonable SKU. See the cost model section below for the full breakdown.

Open mirroring scales surprisingly well

The ingestion engine that processes landing zone files is an off-capacity service run by Microsoft. It does not matter whether you are on an F2 or an F256 — the ingestion throughput is the same. One Microsoft engineer demonstrated 1.2 billion rows per minute ingestion on an F2 in a published benchmark. Two caveats on that figure: the write-side compute — generating and uploading the files — had its own cost not reflected in Fabric capacity usage, and the conditions were artificial. The "free" part is the Fabric ingestion engine; whatever writes files to the landing zone bears its own cost. See the latency section below for the full benchmark context.

Mirroring as a reporting replica — source protection without a read replica

If your organisation only has access to a production source and wants to protect it from heavy analytical queries, a mirrored database is a clean solution: all reporting traffic hits OneLake, not the source. The SQL analytics endpoint provides a T-SQL-queryable replica; Direct Lake provides a Power BI-queryable one. Neither touches the source at query time.

This works best with Azure SQL Database (Change Feed) and SQL Server 2025 (Change Event Stream), where the source-side overhead of the replication mechanism is minimal. SQL Server 2016–2022 with CDC does add some source overhead — capture jobs and log space — which partially offsets the protection benefit, though query traffic is still eliminated. One hard constraint: if your organisation already routes reporting traffic to an Always On availability group secondary, mirroring cannot connect to the secondary — it requires the primary. In that scenario, mirroring does not help.

Cross-database queries work out of the box

The SQL analytics endpoint created for each mirrored database can query across multiple mirrored databases in the same workspace using three-part naming. If you are mirroring a source that spans multiple databases, you can join across them in a single SQL query without any additional configuration.

CI/CD is supported via Git integration and deployment pipelines — with one manual step

Mirrored databases can be committed to a Git repository and deployed through Fabric deployment pipelines. The database definition is stored as a {name}.MirroredDatabase folder containing mirroring.json, which captures the connection and configuration settings.

The important caveat: a mirrored database does not start replicating automatically after deployment. After each pipeline deployment, you must manually start or resume mirroring in the target workspace. Configuration promotion is automated; the replication start is not. That is a meaningful improvement over no CI/CD support at all, but it stops short of a fully automated deploy-and-run story.

The downstream payoff: Direct Lake integration

Because mirrored data lands in OneLake as Delta tables, Power BI Semantic Models can connect via Direct Lake mode. Direct Lake reads Parquet files directly from OneLake without importing data into the model and without querying the SQL analytics endpoint at query time. As new changes land from the source, reports reflect them without a scheduled refresh. The Delta files are the model. For large datasets, this is significantly faster than DirectQuery and avoids the storage cost of Import mode.

The clearest downstream win: source-to-semantic with no transform layer

Not every reporting use case requires transform layers. Operational dashboards, self-service analytics on source tables that are useful as-is, operational metrics that don't require heavy cross-domain joins: these can go directly from mirrored Delta tables to a Direct Lake Semantic Model without any transformation compute at all. Source → mirrored database → Direct Lake Semantic Model is near-real-time, near-zero capacity cost, and requires no Spark jobs or pipeline runs.

For use cases that fit this pattern, mirroring delivers on its promise. If your instinct is to build transform layers on top of mirrored data, ask first whether they are actually serving a reporting requirement or carrying over a pipeline pattern that mirroring has made redundant.

Latency — what "near real time" actually means

The mirroring overview describes replication as "near real-time". No specific latency SLA is published.

Microsoft describes replication latency as 15–60 seconds. For CDC-based native database mirroring (Azure SQL, SQL Server, PostgreSQL, MySQL, Cosmos DB), practitioners report typical latency in the 60–90 second range under normal load — the lower end of Microsoft's stated range appears to reflect optimal conditions rather than typical deployment. Latency can fall further behind under heavy source write pressure. These are community observations rather than confirmed measurements. BigQuery uses a different change capture mechanism (Storage Write API) and may have different latency characteristics — I have not seen reliable published figures for it.

There is an important distinction between two latency layers that the docs don't make explicitly:

  1. Delta table latency — how long after a source change before the Delta table in OneLake reflects it. This is what the replication engine controls.
  2. SQL analytics endpoint latency — how long after the Delta table is updated before queries via the SQL endpoint see the new data. The SQL endpoint always lags the Delta layer.

One question that comes up when evaluating mirroring against watermark-based incremental pipelines is how late-arriving data is handled. For CDC-based mirroring, watermarks are largely irrelevant — and that is mostly an advantage. CDC captures changes in commit order at the source regardless of business timestamps on the rows. If a batch job inserts six-month-old data into the source today, mirroring replicates those rows when they are committed; it does not need a high-water mark to detect them. The one edge case to be aware of is long-running transactions: CDC captures changes at commit time, not at statement time, so a large transaction that runs for two hours before committing will appear in the mirror as a burst at the point of commit rather than spread across the transaction duration.

A published benchmark by a Microsoft engineer under optimal append-only conditions (5 × 32-core machines writing aggressively to an F2 capacity) measured Delta table lag at 11.3 seconds and SQL endpoint availability at 30–60 seconds after file upload. These are best-case figures under a specific workload configuration, not typical figures — the author explicitly describes the results as "empirical results from hacking around tunables" rather than a reproducible benchmark. Read them as an upper bound on how fast the system can go, not as what you should expect in a typical deployment. The benchmark also did not include any updates or deletes — only appends. For applications that need the freshest possible data, read directly from the Delta layer via Spark rather than via the SQL analytics endpoint.

Cost model

One disclosure worth making explicit: the Fabric mirroring overview states that compute and storage are free, with no exceptions noted. In practice, Google BigQuery charges for CDC compute, Storage Write API, and BigQuery storage, and SAP charges SAP Datasphere Premium Outbound Integration pricing. These are charged by the source-side provider, not Microsoft, but they are real costs that belong in your model.

Cost component Charged? Notes
Replication compute No Off-capacity; free for all mirroring types
OneLake storage for mirrored data No (up to limit) 1 TB free per capacity unit (e.g. 64 TB free on F64); excess charged at standard OneLake rates
OneLake write transactions (landing zone writes) Yes Applies to Open Mirroring; files < 4 MB cost one transaction each — see below
Query compute (SQL endpoint, Spark, Power BI) Yes Charged at standard Fabric capacity rates
Source-side costs (BigQuery, SAP, Snowflake) Yes (varies) Charged by the source provider, not Microsoft

What "free ingestion" actually means in practice. The replication engine runs off-capacity — confirmed by independent benchmarking and a Microsoft PM. On an F64, practitioners have reported background CU usage at around 3–4% for half a billion rows across 50 tables. Storage is free at 1 TB per capacity unit; an F64 gives 64 TB, which most organisations will not exceed. The capacity is only required for the initial setup; once configured, the replication engine continues running even if capacity is paused.

To put the cost in perspective against a pipeline-based alternative: a well-optimised incremental pipeline (parameterised loads from multiple on-premises SQL sources, landing as Parquet and merging into Delta tables) can land at a similar absolute CU figure. But that pipeline runs once a day. Pipeline activities and Spark notebooks are background operations in Fabric's CU model, meaning their consumption is smoothed across a 24-hour window. When a pipeline runs once a day, those background CUs spread comfortably across the full window. Run the same pipeline five times a day and you compress five times the background CU consumption into the same budget — already saturating an F16 at that cadence. At sub-minute frequency it becomes unworkable on any reasonable SKU.

Mirroring sidesteps this entirely: it delivers changes continuously at near-zero background CU cost. For teams already running daily incremental pipelines, adopting mirroring is not primarily a cost trade-off — it is a step change in data freshness at no additional ingestion cost.

The net result for a typical database mirroring setup: if your source is Azure SQL, SQL Server, PostgreSQL, MySQL, or Cosmos DB, and you are querying the replica at modest frequency, your Fabric cost for mirroring is close to zero beyond storage. The cost grows once you start querying at scale: the ingestion compute cost is eliminated, not the cost of reading or transforming data.

Open Mirroring write transactions. The ingestion compute is off-capacity and uncharged, but writing files to the landing zone consumes OneLake write transactions, which are charged. One transaction is charged per file smaller than 4 MB; one per 4 MB block for larger files. At a typical small-record size of 100–150 KB per file, writing one million files costs one million transactions — four times more than if those records were batched into 4 MB files. A community report documented consuming over 3.7 million CU-seconds on an F64 (more than half the capacity's daily budget) from a single initial load of approximately 1.5 million small Parquet files; a Microsoft engineer confirmed this was expected behaviour, not a bug. If you control the writer, target file sizes of 4 MB or larger and batch aggressively for initial loads. A secondary issue: very large numbers of small files can cause OOM conditions in the mirroring backend, degrading throughput — a Microsoft engineer acknowledged this as a known issue as of late 2024; verify current status before pushing millions of small files.

Mirroring is a current-state replica

Mirroring is a continuously updated copy of what the source looks like right now. That is a legitimate and valuable thing — but it is not a historical record, and it cannot be used as one. If your architecture requires an append-only, replayable capture of source changes, mirroring does not provide it.

Here is why:

Stop/restart reseeds from current state. If you stop mirroring and restart it, or delete and recreate the mirrored database item, Fabric reseeds from the source's current state. You do not get a replay of historical changes — you get today's data. This behaviour is documented across all SQL-family sources and Cosmos DB. Practitioners confirm it: in a community post, one user described stop-and-restart as "generally a bad idea, since the parquet files that make up the table are no longer kept."

Deletes are applied to the mirror. When a row is deleted at the source, it is deleted from the Delta table in OneLake. It does not persist as a tombstone or soft-delete record. The data is gone from the replica. Delta time travel provides a short window to query past states (1 day for mirrored databases created after mid-June 2025, 7 days for older ones by default; the retention period is configurable via the portal or API) but this is not a rebuild window for most organisations.

PostgreSQL TRUNCATE is not replicated. If the source table is truncated, the mirror retains the pre-truncation data. The mirror silently diverges from the source. This means the mirror is not even a faithful current-state replica for PostgreSQL workloads that use TRUNCATE.

Cosmos DB TTL-deleted rows are not replicated. Rows deleted via Cosmos DB's time-to-live mechanism do not appear as deletes in the mirror. The rows remain in the mirrored table indefinitely, silently diverging from the source.

If historical replay matters to your architecture, you need a separate capture layer alongside the mirror.

What actually replicates — the data type story

Unsupported data types are the most common unexpected blocker when setting up mirroring. The critical distinction the docs don't emphasise up front: unsupported types do not always block the table. The impact depends on where the unsupported type appears.

Scenario Impact
Unsupported type in a regular column Column is silently excluded; the rest of the table mirrors
Unsupported type in a primary key or clustered index column Entire table is blocked
Unsupported type used as a table feature (Always Encrypted, in-memory, etc.) Entire table is blocked

For the SQL-family sources, the full blocklist is documented across the individual limitations pages (Azure SQL Database, SQL MI, SQL Server, PostgreSQL, MySQL). A few highlights worth calling out:

Tables with json or vector columns are completely blocked (not just column-skipped) for Azure SQL Database. This is an all-or-nothing table exclusion, not a column exclusion. The table cannot be mirrored at all. hierarchyid, datetime2(7) as a primary key, and datetimeoffset(7) as a primary key have the same effect.

PostgreSQL excludes a long list of column types silently, including all geometric types, all network address types, all range types, json, jsonb, xml, and interval. None of these block the table — they simply disappear from the replica. The PostgreSQL limitations page documents the full list.

Oracle uses an allowlist, not a blocklist. Only fifteen specific types are supported. Any Oracle type not on that list — including CLOB, BLOB, XMLTYPE, and SDO_GEOMETRY — is implicitly excluded.

NUMBER without explicit precision or scale is a hard failure for Oracle. This is a common Oracle pattern: col NUMBER rather than col NUMBER(10,2). Multiple practitioners have reported that such columns cause the error Invalid Decimal Precision or Scale. Precision: 38, Scale: 127, blocking the entire table from mirroring. There is no workaround within mirroring — the feature does not support custom SELECT queries that could add an explicit cast. Changing a production Oracle column type is typically not feasible, which means affected tables must be handled outside mirroring via pipelines or copy jobs.

DDL changes behave differently across sources. Azure SQL picks up ADD COLUMN automatically. PostgreSQL requires a stop-and-restart of replication to pick up any schema change. MySQL's replication is disrupted by DDL changes. SQL MI does not support ALTER COLUMN or RENAME COLUMN while a table is being mirrored; those operations are blocked outright. Check the limitations page for your specific source before planning a schema migration on a mirrored database.

Operational limits and gotchas

Beyond the data type limitations, several operational limits are worth knowing before committing to mirroring in production.

Use a service account, not an individual. A mirrored database is permanently tied to the user who created it. There is no ownership transfer mechanism. If the owner leaves the organisation, the item must be deleted and recreated. The connection is also tied to the item owner's Entra ID authentication: if their token expires (due to MFA re-prompt, device compliance failure, or account deactivation) replication stops. A Microsoft MVP documented (Jul 2024) that workspace and tenant admins cannot access the connection unless the original owner has shared it first. Create all mirrored database items using a service principal or a shared service account, and share the connection with an admin group immediately after creation.

Private link support is partial — and most connectors are unsupported. This is a significant blocker for enterprise environments with strict network security requirements. When Fabric's "Block Public Internet Access" tenant setting is enabled, most database mirroring connectors are not supported: active mirrored databases enter a paused state and mirroring cannot be started.

Status Connectors
Supported Open Mirroring, Azure Cosmos DB, Azure SQL Managed Instance, SQL Server 2025
Blocked Azure SQL Database, PostgreSQL, MySQL, Oracle, Snowflake, BigQuery, SAP

A further constraint: on-premises data gateways (required for Oracle, and for SQL Server in many on-premises deployments) fail to register when private link is enabled; VNet data gateways work as a substitute but require separate provisioning. If your organisation has enabled or is planning to enable Fabric private link, verify connector support before building a mirroring architecture around a connector that will not function in that network configuration.

CDC requirements vary significantly by source. Whether mirroring requires CDC to be enabled on the source database depends on which source and version you are using:

Source Mechanism used Source-side requirement
Azure SQL Database SQL Change Feed None — no CDC required
Azure SQL MI SQL Change Feed (newer) / CDC (SQL 2022 policy) Depends on update policy
SQL Server 2016–2022 CDC CDC must be enabled on the source database
SQL Server 2025 Change Event Stream CDC must not be enabled — incompatible
PostgreSQL Logical replication wal_level = logical required
MySQL Binary log replication Binary logging required
Oracle LogMiner Archive log mode and supplemental logging required
Snowflake Snowflake Streams Change tracking on tables
Cosmos DB Cosmos DB change feed Built-in — no configuration required
BigQuery BigQuery CDC (Storage Write API) CDC must be enabled per table; Google charges for CDC compute and Storage Write API
SAP SAP Datasphere change capture Handled by SAP Datasphere — no direct source-side config; Datasphere must be separately licensed

The SQL Server 2016–2022 CDC requirement is the most operationally significant. CDC writes captured changes to dedicated tables in the source database, consumes transaction log space, and requires active management to prevent log fill. On a busy SQL Server, DBAs often resist enabling it. If the transaction log fills and is truncated before mirroring can process it, the mirror reseeds from current state rather than resuming incrementally. Azure SQL Database and SQL Server 2025 use newer architectures (Change Feed and Change Event Stream respectively) that carry meaningfully lower source-side overhead. If you have a choice of source version, the newer architecture is worth preferring. If DBA approval for source-side config is uncertain, Open Mirroring requires none of it — see the decision framework in the "Choosing your path" section.

Availability group secondaries are not supported for SQL Server. Fabric Mirroring for SQL Server requires connection to the primary database of an Always On availability group. Connecting to a secondary — even a readable secondary designated for reporting workloads — is not supported. Organisations that deliberately route external connections away from the primary for load isolation will find this a hard blocker.

Deletion vectors break some Python Delta readers. When rows are deleted from a source and replicated to Fabric, the Delta table uses deletion vectors — a Delta Lake protocol feature that marks deleted rows without immediately rewriting Parquet files. Spark handles deletion vectors correctly, as does DuckDB version 1.2 and above. Polars (via delta-rs) does not: it raises DeltaProtocolError: The table has set these reader features: {'deletionVectors'} but these are not yet supported. This was confirmed by community reports and acknowledged by Microsoft engineers in May 2025. If your notebooks use Polars to read mirrored Delta tables, the reads will succeed until the first delete is replicated, then fail. Use Spark or DuckDB for Delta reads against mirrored tables.

Reseed behaviour and automatic recovery. If Fabric capacity is paused for an extended period, the source database's transaction log may be truncated before mirroring can resume, triggering a reseed from the current source state. For Azure SQL Database and Azure SQL Managed Instance, automatic reseed is now enabled by default: rather than staying broken, mirroring reinitialises automatically. Two triggers exist: table-level reseed for DDL changes (add, drop, alter, or rename column; truncate or rename table; add nonclustered primary key) and database-level reseed when the transaction log exceeds a configured threshold. SQL Server 2025 supports automatic reseed but it is disabled by default. In all cases, reseed reinitialises from current source state — the improvement is operational resilience, not historical fidelity.

Structured replication logs exist via Workspace Monitoring. Enable Workspace Monitoring for your workspace and replication events are written to an Eventhouse KQL database automatically. The MirroredDatabaseTableExecution table records ProcessedRows, ProcessedBytes, ReplicatorBatchLatency, OperationStartTime, OperationEndTime, and ErrorMessage per operation, enough to query replication history, measure lag over time, and surface failures. Workspace Monitoring is not enabled by default and is charged at standard Eventhouse rates. The events are emitted automatically once configured; you are building queries on top of the data, not the capture layer itself.

Minor configuration limits. Several smaller constraints worth knowing: the maximum table count per mirrored database is 1,000 — sources above this threshold must be split across multiple items. Every mirrored database automatically creates a paired SQL analytics endpoint that cannot be deleted or disabled independently. For MySQL, only one database per server instance can be mirrored, and tables cannot be added or removed after initial setup.

Security and governance

Row-level security (RLS), column-level security (OLS), and dynamic data masking configured in the source system are not propagated to the mirrored database. This is documented for all SQL-family sources and applies universally. A user who is restricted from seeing certain rows or columns in the source database will have no such restrictions applied when querying the mirrored replica via the SQL analytics endpoint or Spark, unless those controls are manually re-configured in Fabric.

This is not a mirroring bug. It is an architectural consequence of the data moving to a different system. But it is a significant governance consideration for organisations with row-level security in their source databases. Any security model that relies on source-database RLS must be rebuilt entirely at the Fabric layer.

I did not run empirical tests on RLS behaviour at the SQL analytics endpoint, cross-tenant sharing scenarios, or the interaction between workspace permissions and item-level permissions. The documentation on these topics is thin. Before deploying mirroring for data with regulatory or contractual access controls, test the security model explicitly — do not infer from the source database's configuration.

Choosing your path

The evaluation is two-dimensional. Your source constrains what is even possible; your requirements determine whether what is possible is actually suitable. Most practitioners inherit their source — they do not choose it. Start the evaluation there.

Phase 1: Source assessment

1. Does your source have a native connector, and how mature is it?

Connector tier Sources Guidance
Mature Azure SQL Database, Azure SQL MI, SQL Server, PostgreSQL Well-documented, production-validated; proceed to step 2
Established with known limits MySQL, Cosmos DB, Snowflake Documented with specific constraints; review appendix before proceeding
Sparse documentation Oracle, BigQuery, SAP, Dremio Significant gaps in published behaviour; treat — cells in appendix as unknowns requiring direct testing; budget validation time before committing
No native connector Anything else Jump to Phase 1, step 4

2. Are there hard blockers for your specific source?

Check these before going further. Any one of them may end the native mirroring evaluation:

  • Oracle: NUMBER columns without explicit precision/scale cause table-level failures; On-Premises Data Gateway required in all environments including cloud-hosted Oracle
  • MySQL: Burstable compute tier unsupported; only one database per server can be mirrored; tables cannot be added or removed after initial setup
  • SQL Server: Availability group secondaries not supported — connection must be to the primary
  • Any source: If your Fabric tenant has "Block Public Internet Access" enabled, check the private link support list — most connectors are not supported and will enter a paused state

3. Can you get source-side configuration approved?

Configuration requirements vary significantly by source and typically require DBA or infrastructure team approval:

Source Requirement Overhead
Azure SQL Database None — Change Feed is built-in Zero
SQL Server 2025 None — Change Event Stream is built-in Zero
Cosmos DB None — change feed is built-in Zero
SQL Server 2016–2022 CDC must be enabled on the database Moderate — log space, active management
PostgreSQL wal_level = logical required Low — server restart may be required
MySQL Binary logging required Low
Oracle Archive log mode + supplemental logging + LogMiner access High — significant DBA engagement typically required
BigQuery CDC must be enabled per table Low — but Google charges for CDC compute and Storage Write API
SAP Handled by SAP Datasphere High — Datasphere must be separately licensed and configured

If approval is uncertain or refused, native mirroring is blocked regardless of requirements. Go to step 4.

4. If no native connector, or source-side config not approvable: can you use Open Mirroring?

  • Can you read changes from the source using existing mechanisms — Change Tracking, RowVersion, date-modified timestamps, triggers?
  • Can you run a process that writes Parquet files to OneLake?
  • Yes to both → Open Mirroring is your path. You own the change detection logic; no source-side CDC configuration is required.
  • No → Traditional pipeline or CDC stack. Mirroring in any form is not available for this source.

Phase 2: Requirements fit

Only reach this phase if Phase 1 confirmed a viable source. These questions determine whether what is available is actually suitable.

5. What is the reporting use case?

  • Operational reporting on current source state, minimal or no transforms → source-to-semantic with Direct Lake; this is mirroring's clearest win. Proceed.
  • Reporting that requires transforms (cleaning, joins, aggregations) → mirroring handles ingestion; plan compute budget for the transform layers separately. Near-real-time end-to-end requires Spark Structured Streaming or high-frequency micro-batches — neither is free. Decide whether that compute cost is justified before committing to the architecture.

6. Do you need a replayable raw layer?

  • Yes, and unwilling or unable to maintain one alongside the mirror → mirroring alone is insufficient. Use a traditional pipeline, or use mirroring for current-state reporting while maintaining a separate raw capture.
  • No, or able to maintain one separately → proceed.

7. Do you need source-level RLS or column security to propagate to Fabric automatically?

  • Yes → mirroring is the wrong tool regardless of source. Security policies are not propagated; they must be rebuilt at the Fabric layer.
  • No → proceed.

8. Do you need a guaranteed, SLA-backed latency?

  • Yes → mirroring has no published SLA. Use a scheduled pipeline for predictable, measurable timing.
  • Near-real-time is sufficient, SLA not required → mirroring is a fit.

Verdict

After following mirroring's development closely without yet committing to it in production, the constraints that have most consistently given me pause are the missing replay semantics — which make it an imperfect fit for architectures that require a replayable raw layer — and, for enterprise environments, private link incompatibility across most connectors.

Mirroring is well-suited for: near-real-time operational reporting where the mirror reflects current source state; replacing DirectQuery with Direct Lake on large datasets; reducing ETL pipeline complexity where you don't need historical replay; Open Mirroring as a generic ingestion mechanism for sources without a native connector.

Mirroring is a poor fit for: any architecture that requires historical replay or pipeline replayability; ingestion where append-only, idempotent semantics are required; sources with Oracle NUMBER columns, MySQL on Burstable compute, or SQL Server availability group secondaries; workloads that require security policies from the source to be automatically enforced in Fabric.

A note on documentation maturity as a risk signal. The gaps in the appendix matrix are not editorial omissions: they are behaviors that Microsoft has not published documentation for. If the vendor of a feature cannot tell you whether TRUNCATE is replicated, or how a DDL change is handled, you will find out the answer in production. The connectors with the most — entries in the appendix — BigQuery, SAP, Oracle, Dremio — are also generally the less mature ones. Factor testing time into your evaluation accordingly, and do not assume that absence of a documented limitation means the limitation does not exist.

What to watch: the extended capabilities (Delta change data feed, view mirroring) are currently free but are paid features once billing is enabled; the documentation confirms billing is temporarily disabled. If you build on these capabilities, budget for the eventual charge. SQL Server 2025 and the Change Event Stream architecture (available on Azure SQL Database and SQL MI) are meaningfully better than the CDC-based approach used for older SQL Server versions — if you have a choice of source version, prefer the newer architecture.

Mirroring is one of the more genuinely compelling things in the Fabric toolkit — real-time ingestion at near-zero cost is a meaningful offer. The qualification is precision: it solves a specific problem well, and the more clearly you can state that problem before you start, the less likely you are to discover its limits in production.
